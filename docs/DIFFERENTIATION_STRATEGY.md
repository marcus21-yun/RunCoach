작성일: 2026-09-26
상태: 제안. 기능 구현·출시·사용자 검증이 완료되었다는 의미가 아니다.

## 1. 추천 포지셔닝

**지난 러닝과 내 피드백을 기억하고, 오늘 할 행동 하나를 알려주는 한국어 러닝 코치.**

초기 고객 가설은 Galaxy Watch를 사용하는 40~60대 입문·복귀 러너다.
우선 5km를 꾸준히 달리려는 사용자에게 집중하고, 이후 10km·하프 준비로 확장한다.
연령만으로 운동 능력이나 음악 취향을 추정하지 않는다.

고객이 해결하려는 질문은 “오늘 얼마나 뛰어야 하지?”, “지난번 힘들었던 점을 어떻게 바꾸지?”,
“며칠 쉬었는데 다시 시작해도 될까?”다. 실제 훈련 강도 규칙은 별도 전문 검토와 검증이 필요하다.

소개 문구 제안: **“오늘의 한 걸음부터, 나를 기억하는 런코치.”**

## 2-1. Apple Watch·Galaxy Watch 기본 러닝 경험과의 비교

2026-09-25 공식 지원 문서 확인 기준. 기기·OS·지역별 지원은 출시 전 다시 확인한다.

| 구분 | Apple Watch (운동 앱) | Galaxy Watch (Samsung Health) | 런코치가 겨냥하는 빈자리 |
|---|---|---|---|
| 체감 난이도 | 운동 후 1~10 노력 점수(자동 추정 + 수동 조정) → 7일/28일 훈련 부하 추세 | Running Coach가 개인화 프로그램 제공(Watch8 대상) | 체감 응답이 **다음 러닝 목표를 즉시 바꾸고 그 이유를 한 문장으로** 보여준다 |
| 음성 코칭 | Workout Buddy: Apple Intelligence 지원 iPhone·블루투스 헤드폰 필요, 영어·스페인어 | 기기·언어별 확인 필요 | 한국어 짧은 안내, 워치 단독·오프라인 규칙 기반 대체 안내 |
| 쉬었다 다시 시작 | 훈련 부하 추세로 확인 | 확인 필요 | 공백 일수를 사실대로 알려주고 복귀 거리(60%/80%)를 자동 제안 |
| 설명 가능성 | 지표·추세 중심 | 프로그램·지표 중심 | 숫자는 검토 가능한 규칙이 결정, 근거는 “저장된 기록·내 응답”만 인용 |

결론: 체감 점수 수집 자체는 Apple도 제공하므로 차별점이 아니다.
런코치의 차별점은 **“응답 1탭 → 다음 목표 변경 → 근거 표시 → 다음 러닝 전 다시 상기”의 닫힌 고리**를
입문·복귀 러너가 폰 없이 워치에서 완결하도록 만드는 것이다. 이 역시 파일럿으로 검증할 가설이다.

### 구현 현황 (2026-09-25, 빌드·실기기 검증 전)

- `core/.../coach/MemoryCoach.kt`: 규칙 엔진. 체감(쉬움/적당/힘듦) + 완주 여부 + 공백 일수 + 최근 3회 패턴으로
  다음 목표(BUILD/HOLD/EASE/RETURN)와 근거 문장을 계산한다. 거리 증가는 10%·최대 1km, 거리를 늘릴 때 페이스는 유지.
  체감 응답이 없으면 센서 피로도로 판단하고 그 사실을 근거에 밝힌다. 단위 테스트 13건.
- `wear/.../data/CoachPlanner.kt`: 기록에 체감 응답을 저장하고 워치에서 다음 목표를 재계산한다(폰·네트워크 불필요).
  폰이 보낸 미수락 목표가 있으면 덮어쓰지 않고, 폰 목표가 도착하면 코치 근거를 비운다.
- 러닝 후 화면: “오늘 어땠나요?” 3버튼 → “기억했어요 ✓”와 오늘 할 행동 한 문장.
- 다음 목표 화면: “이렇게 판단했어요” 근거 목록. 시작 전 화면: 수락한 코치 목표의 행동·이유 1줄.
- 러닝 후 “지난주 대비”가 방금 저장된 자기 기록과 비교되던 문제를 이전 기록 기준으로 수정.

남은 작업: 실기기 빌드·원형 화면 잘림 확인, 체감 응답의 Supabase 동기화 컬럼, 웹 수정·삭제 화면,
사전 음성 브리핑 프롬프트에 코치 근거 전달.

## 3. 가장 먼저 만들 차별화 경험

### A. 기억하는 코치: 지난 피드백 → 오늘 한 가지 → 다음 확인

- 러닝 후 사용자가 `쉬웠어요 / 적당해요 / 힘들어요` 중 하나를 선택한다.
- 사용자가 동의한 목표, 최근 완료 기록, 피드백, 선호하는 코칭 빈도를 구조화해 저장한다.
- 다음 시작 화면에 오늘 목표와 이유를 한 문장씩 표시한다.
- 러닝 종료 후 오늘 실천 결과를 확인하고 다음 러닝에 반영한다.
- 기억한 내용은 웹에서 확인·수정·삭제할 수 있다. 기록이 없으면 모른다고 표시한다.

예시: “지난번에 초반이 힘들었다고 하셨어요. 오늘은 처음 구간을 여유 있게 시작해볼까요?”
실제 사용자 피드백이 있을 때만 이런 문장을 생성한다.

수용 기준: 브리핑의 숫자는 저장된 기록과 일치하고, 사용자 피드백이 다음 제안의 근거에 표시된다.
개인화의 가치는 ‘말투가 바뀜’보다 ‘내 피드백이 다음 행동을 바꿈’으로 평가한다.

### B. 덜 보게 하는 워치: 한 화면, 한 행동

- 홈: 오늘 목표 + 이유 + 시작 버튼.
- 달리는 중: 사용자가 선택한 핵심 수치 1개를 크게, 보조 수치 2개와 일시정지 조작 제공.
- 코칭: 짧은 한국어 안내와 구분 가능한 진동. 사용자가 빈도를 낮추거나 끌 수 있다.
- 종료: 실천한 점 1개, 체감 난이도 선택, 저장·동기화 상태.
- 연결이 끊겨도 기록을 보존하고 기본 안내가 동작하도록 설계한다.

수용 기준: 초기 권한 설정 이후 홈에서 시작까지 2탭 이내를 목표로 실기기에서 측정한다.
원형 화면 잘림, 큰 글자, 야외 가독성, 일시정지 오조작을 확인한다.

### C. 복귀를 돕는 주간 리포트

- 빠른 기록 순위 대신 실행한 횟수, 스스로 선택한 목표, 다음 가능한 일정을 보여준다.
- 쉬었던 주에는 기록 공백을 사실대로 설명하고 가능한 일정부터 다시 선택하게 한다.
- 웹에서 일정을 바꾸면 워치의 다음 목표와 동일한 버전으로 연결한다.
- ‘건강 점수’나 ‘부상 예측’처럼 검증되지 않은 의학적 표현을 만들지 않는다.

수용 기준: 주간 리포트에서 선택한 다음 행동을 워치에서 확인할 수 있고, 변경 이유를 사용자가 이해한다.

## 4. 기능 우선순위

점수 대신 가치·의존성·검증 비용으로 우선순위를 정했다. 개발 일정은 아래의 추정안이다.

| 순서 | 범위 | 고객 가치 | 선행 조건 | 판단 |
|---|---|---|---|---|
| P0 | 기록 보존, 인증, 계정 연결, 동기화 | 기록을 잃지 않고 기기를 바꿔도 이어짐 | 스키마·기록 ID·소유권 정리 | 기반 작업 |
| P1 | 워치 화면 개선 + 기억하는 코치 최소 기능 | 매번 무엇을 할지 바로 이해 | 피드백 저장, 근거 검증 | 첫 차별화 출시 |
| P2 | 웹 주간 리포트 + 다음 일정 변경 | 다음 러닝으로 자연스럽게 이어짐 | 웹앱 저장소 확인, 인증·동기화 | 첫 웹 연동 범위 |
| P3 | 코칭 빈도·말투 개인화 | 불필요한 안내 감소 | 실제 사용 피드백 | 소규모 확장 |
| 실험 | 음악 추천 | 러닝 준비 편의 | 재생 연동 실기기 검증 | 핵심 출시와 분리 |
| 보류 | 공개 커뮤니티, 순위, 가족 자동 통지 | 추가 가치 가능 | 운영·동의·신뢰 설계 | 초기 범위 제외 |

음악의 첫 실험은 사용자가 선택한 플레이리스트를 시작 전에 여는 수준으로 제한한다.
Google은 Wear OS의 YouTube Music 사용을 안내하지만, 이 문서가 타 앱의 무인 자동 재생·전환 API를 보장하지는 않는다.
기존 음악 PRD의 검색 링크 자동 재생, 로그인 불필요, 비구독 광고 재생은 구현 전 검증할 가정이다.
심박수 상승을 음악 전환이나 운동 독려의 단독 근거로 사용하지 않는다.
출처: [Google Wear OS 음악 사용 안내](https://support.google.com/wearos/answer/11167087?hl=en).

## 5. 웹앱 연동 설계 제안

웹은 주간 계획·기록 해석·설정, 워치는 시작·실행·짧은 피드백, 폰은 연결·권한·동기화를 맡는다.
기존 웹앱의 코드와 배포 환경은 이 저장소에서 확인되지 않았으므로 새 프레임워크나 호스팅은 아직 정하지 않는다.

현재 코드에서 확인한 사실:
- `OwnerIdProvider.kt`: SharedPreferences에 기기 로컬 UUID를 생성한다. 웹 로그인 사용자와 연결되는 계정 ID가 아니다.
- 앱 `SupabaseSyncService.kt`: 이 UUID를 `owner_id`로 전송하며 API 키 기반 요청을 구성한다.
- `wear/.../OpenAiApiService.kt`와 `wear/build.gradle.kts`: 워치에서 모델 API를 직접 호출하고 로컬 키를 BuildConfig에 주입한다.
- `BriefingRepository.kt`: 브리핑 캐시와 템플릿이 있어 오프라인 대체 안내의 기반으로 검토할 수 있다.
- 저장소의 SQL 존재는 운영 DB에 동일하게 적용되었다는 증거가 아니다.

제안하는 작업 순서:
1. 실제 웹앱과 운영 DB 상태를 확인하고 기존 데이터의 백업·이전 계획을 만든다.
2. 웹·폰 사용자 계정을 연결하고, 기기 로컬 기록은 명시적인 소유권 확인 후 계정으로 이전한다.
3. 워치는 폰의 승인된 페어링 흐름을 통해 연결한다. 서비스 권한 키를 앱에 배포하지 않는다.
4. 기록별 안정적인 ID를 두고 재전송해도 중복 생성되지 않도록 한다. 로컬 저장 후 재시도 큐로 동기화한다.
5. 실행 기록은 임의 덮어쓰기를 피하고, 계획 수정은 버전 충돌을 감지해 최신 상태를 다시 읽는다.
6. 사용자별 읽기·쓰기 권한을 점검하고 다른 계정의 기록 접근이 거부되는지 검증한다.
7. 모델 호출은 인증된 서버 경유로 옮기고 사용량 제한·응답 검증·캐시를 적용한다.
8. 웹은 주간 기록 읽기부터 연결하고, 다음 단계에서 계획 수정과 워치 반영을 추가한다.

완료 조건: 동일 기록 재전송 시 중복 없음, 오프라인 후 복구, 계정 간 접근 거부,
기록 이전 전후 개수·핵심 값 일치, 웹에서 변경한 계획이 워치에 반영됨.

## 6. 방어 가능한 가치와 AI의 역할

한국어 문장 생성이나 코치 캐릭터만으로는 모방을 막기 어렵다.
반복 사용 과정에서 어떤 제안이 실제 실천으로 이어졌는지 검증하고,
그 결과를 화면·안내 빈도·개인화 규칙에 반영하는 운영 역량을 축적한다.
이는 경쟁 우위 가설이며 현재 확보한 자산이라고 주장하지 않는다.

훈련 수치와 알림 조건은 검토 가능한 규칙이 결정하고, 생성형 AI는 그 근거를 짧게 설명하는 역할을 맡긴다.
데이터가 부족하거나 생성이 실패하면 정해진 안내로 대체한다.
센서만으로 건강 상태를 진단하거나 안전을 보장하는 표현은 제공하지 않는다.

## 7. 6주 실행안과 검증

1인 개발 기준의 가설 일정이며, 인증·데이터 이전 규모와 실기기 이슈에 따라 조정한다.

| 기간 | 산출물 | 다음 단계로 넘어갈 조건 |
|---|---|---|
| 1주차 | 목표 고객 5명 인터뷰, 워치 사용 관찰, 데이터·웹 현황 점검 | 반복되는 문제와 첫 사용 흐름 확인 |
| 2주차 | 계정·동기화 설계 및 워치 화면 시안 | 기록 이전 방식, 화면 가독성 검토 |
| 3~4주차 | 기록 기반 브리핑·체감 피드백·기본 동기화 구현 | 데이터 누락·중복·권한 검증 통과 |
| 5주차 | 웹 주간 리포트와 다음 일정 연결 | 웹→폰→워치 반영 검증 |
| 6주차 | 10~20명 파일럿 시작, 실패·비용 계측 | 4주 관찰 계획과 측정 이벤트 확인 |

4주 유지율은 파일럿 시작 후 4주가 지나야 평가하므로 6주차에 결과가 나온다고 가정하지 않는다.

### 핵심 측정 지표

아래 목표값은 시장 기준이 아닌 초기 의사결정용 가설이다.
- 첫 러닝 완료율: 온보딩 완료자 중 7일 내 첫 기록 저장 비율, 초기 목표 70%.
- 반복 사용: 첫 러닝 사용자 중 4주차에 한 번 이상 러닝을 기록한 비율, 초기 목표 40%.
- 코칭 도움 평가: 응답한 브리핑 중 ‘도움 됨’ 비율, 초기 목표 70%. 응답률도 함께 보고한다.
- 기록 신뢰성: 검증 시나리오에서 유실·중복 0건. 베타에서는 발생 건수와 원인을 매회 확인한다.
- 비용: 활성 사용자당 월 모델·음성·서버 비용을 실제 측정한다.

이벤트 후보: `onboarding_completed`, `run_started`, `run_saved`, `sync_completed`,
`briefing_feedback`, `next_plan_accepted`. 이벤트에는 원문 건강 기록이나 비밀키를 담지 않는다.
소규모 파일럿은 비율과 함께 분자·분모를 표시하고 인터뷰로 해석한다.
‘기억하는 코치’가 도움이 되지 않는다면 페르소나 추가보다 근거·길이·안내 시점을 먼저 수정한다.

## 8. 유료화와 첫 사용자 확보

- 첫 10~20명은 Galaxy Watch를 가진 목표 고객으로 모집해 4주 사용을 관찰한다.
- 반복 사용 이유가 확인된 뒤, 개인화 주간 코칭과 웹 리포트의 유료 의향을 조사한다.
- 기본 기록·열람·내보내기는 무료 범위 후보, 개인화 코칭·장기 리포트는 유료 범위 후보로 둔다.
- 월 4,900원과 7,900원을 가격 조사 후보로 제시하되, 실제 과금은 원가와 이용 의향 확인 후 결정한다.
- 지속 비용이 발생하므로 무제한 평생 AI 사용권은 초기 상품에서 제외한다.
- 이전 문서의 브리핑 단가·평생 원가·손익분기 사용자 수는 실측 전까지 사업성 근거로 쓰지 않는다.

첫 홍보 소재는 기능 목록보다 “지난 피드백 → 오늘 안내 → 러닝 후 확인”을 보여주는 짧은 시연으로 만든다.
외부 모집 글 게시나 메시지 발송은 이번 문서 작업에 포함하지 않았다.
